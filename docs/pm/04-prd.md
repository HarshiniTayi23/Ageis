# 04 · Product requirements document (PRD)

**Status:** Template · **Owner:** Sri Harshini Tayi · **Reviewers:** _(anyone you can get)_

A PRD answers *what* and *why*, never *how*. The how goes in ADRs and code.

## 1. Summary
_Three sentences: the problem, who has it, what we're building._

## 2. Goals
_What must be true when this ships? Each goal links to a metric in section 5._

## 3. Non-goals
_What we're explicitly not doing, and why. This section prevents more arguments than any other._

## 4. Requirements
Use MoSCoW. Every requirement is testable.

## 5. Success metrics

| Metric | Today (baseline) | Target | How we measure it |
|---|---|---|---|
| Time to find clean recovery point | _from user research_ | < 5 min | demo scenario timing |

Also name one **counter-metric**, something that must not get worse. _(Example: false alarms on normal business changes.)_

## 6. User experience
_The key flows, step by step. The "3 a.m. restore" and "undo agent X" flows at minimum._
